# Ownership and repo boundaries

**Date:** 2026-09-06
**Status:** Decided 2026-09-06. Decisions 5.1–5.6 are taken as recommended below; PRs execute in the order of section 4.
**Repo:** `impresspress` only (upstream items are recorded for Phase 4, not done here)
**Origin:** Phase 2 of `docs/CODE_REVIEW_2026-09-05.md` (section 7); themes T2, T3; bugs B10, B12, B13, B14
**Base verified against:** `bdb2625c` (`phase1/route-table-router-cleanup`, PR #17 merged). Paths are relative to `crates/impresspress-core/src/` unless another crate is named. `routing.rs`, `endpoint_match.rs`, `prepared_plan.rs` and `builder/prepared.rs` were read from `origin/main` because Phase 1 PR 7 is editing them.

## Goal

Every table has exactly one Rust module that spells its name, its column names and its row shape, and every other module reaches the table through that module's functions. Concretely, when this phase is done:

1. `grep -rn 'blocks::admin::\|blocks::auth::[A-Z]\|admin_schema\|messages_schema' crates/impresspress-core/src crates/impresspress-cloudflare/src crates/impresspress/src crates/impresspress-web/src` finds no table constant reaching across a block boundary. `admin_schema.rs` and `messages_schema.rs` do not exist. `auth/mod.rs` no longer re-exports `USERS_TABLE`, `API_KEYS_TABLE` or `RATE_LIMITS_TABLE`.
2. In `blocks/files`, `blocks/legalpages`, `blocks/products/pages.rs`, `blocks/products/handlers` and `blocks/llm`, no file outside a `repo/` directory calls `db::*` or names a `*_TABLE`/`COLLECTION` constant. The `repo_door_test` pattern (`blocks/products/tests/repo_door_test.rs:1-27`) is generalised to enforce this per block.
3. Both snapshot gates (`tests/openapi_snapshot.rs`, `tests/endpoint_surface.rs`) are byte-identical for every PR except the two that deliberately change a declaration: the legalpages PATCH body schema (B10) and the removal of `POST /b/auth/api/oauth/sync-user` (B14). Each such diff is listed line by line in its PR.
4. B10, B12, B13 and B14 are closed by construction, each with a test that fails on the current tree.
5. The auth credential model and the session-row model are decided and implemented, not deferred.

## Why

The review's evidence still holds on the current tree; the line numbers below are re-verified. Where the review's claim was inexact the inventory says so.

- Core reads platform state through the admin *feature block*: `cache_key.rs:9` imports three table constants from `blocks::admin`; `pipeline.rs:554,557` writes request logs to `blocks::admin::REQUEST_LOGS_TABLE`; `boot.rs:24,387,408` seeds variables and loads WRAP grants from `blocks::admin::*`; `config_generation.rs:65,102-113` matches on the same constants. `admin_schema.rs:1-13` describes itself as "the single source", yet `boot.rs`, `cache_key.rs`, `config_generation.rs` and `pipeline.rs` all bypass it, and it lacks `WRAP_GRANTS_TABLE` (declared at `blocks/admin/mod.rs:24`).
- `messages_schema.rs:42-69` exists so `blocks/llm/pages.rs:15,115,136` can `db::list` the messages block's two tables directly, which needs two WRAP grants declared by messages (`blocks/messages/mod.rs:210-218`); the same block writes and lists entries through `call_block` (`blocks/llm/mod.rs:228-274`).
- `auth/mod.rs:49-58` re-exports `USERS_TABLE` "to keep existing consumers on stable identifiers". Six production writers use it with hand-built column maps (inventory 1.2) while typed functions for four of the six writes already exist in `auth/repo/users.rs`.
- Files returns untyped `Record`s from every repo function (`blocks/files/repo/buckets.rs:33-40,53-56,83,97-103`, `repo/shares.rs:38,61,72,82,105,126`, `repo/quota.rs:22,33,42`); six page-side decoders exist, and `public` is decoded as a JSON bool at `pages_user/buckets.rs:152-156` and as the string `"true"` at `pages_admin.rs:269` for a column declared `INTEGER` (`files/migrations/001_initial_schema.sqlite.sql:7`).
- Legalpages has no repo layer: `COLLECTION` at `blocks/legalpages/mod.rs:189`, direct `db::*` at 17 sites across `mod.rs`, `service.rs` and `pages.rs`, the same `(doc_type, status)` filter block copied five times, and a generic PATCH (`mod.rs:143-147` -> `:420-436` -> `crud.rs:153-170`) that applies any column map, including `status`, so `PATCH {"status":"published"}` bypasses `service::publish_document` (`service.rs:56-97`) and leaves two published rows.

## 2. Design

### 2.1 Core `platform_state` module

**2.1.1 Layout.** `crates/impresspress-core/src/platform_state/{mod.rs, variables.rs, block_settings.rs, wrap_grants.rs, request_logs.rs, user_roles.rs}`. Each module owns `pub const TABLE` (names unchanged: `impresspress__admin__*`), a row struct, one `from_record` and one `to_data` so column names are spelled once, and its functions. `user_roles` is included because the framework auth block reads and writes it on every login (`auth/mod.rs:322-424`); leaving it in admin keeps the auth-to-admin import the review calls out. Roles, permissions, audit logs and storage access logs stay admin-owned (only admin reads them).

**2.1.2 Two callers, one codec.** Boot runs before WRAP over `Arc<dyn DatabaseService>` (`boot.rs:79-378`, `features.rs:402-441`); blocks and the pipeline run under WRAP over `&dyn Context`. Both flavours stay, both go through the module's codec:

- `variables`: boot flavour `seed_if_absent`, `set`, `seed_auto_generated`, `seed_and_load`, `load_all` (moved from `boot.rs`); context flavour `list_all`, `get_by_key`, `upsert_by_key`, `delete` (replacing the raw maps in `blocks/admin/{settings,ops}.rs`, `pages/variables.rs`, `dev/seed.rs`). `VariableRow { id, key, value, name, description, warning, sensitive, block, created_at, updated_at }`.
- `block_settings`: boot flavour `load`, `load_and_seed(db, defaults)` (moved from `features.rs:402-541`, see 2.1.4); context flavour `is_enabled`, `set_enabled` (moved from `blocks/admin/settings.rs:25-100`), `upsert_fields` (moved from `migration_helper.rs:313`), `list_all`. `BlockSettingsRow { id, block_name, enabled, current_hash, blessed_hash, seed_defaults_hash, created_at, updated_at }`.
- `wrap_grants`: boot `load(db) -> Vec<ResourceGrant>` (moved from `boot.rs:378`); context `list`, `create`, `delete` (from `blocks/admin/mod.rs:735-790`, `pages/permissions.rs:127,442`). `WrapGrantRow` plus `into_resource_grant`.
- `request_logs`: `insert(ctx, RequestLogRow)` (the struct at `pipeline.rs:508` and the map at `:531-549` become the row and its `to_data`), `paginated`, `list_recent`, `aggregate_daily` for `pages/{logs,network,dashboard}.rs`. The queued/inline mode switch stays in `pipeline.rs`; only the row and the table move.
- `user_roles`: `list_for_user`, `list_for_users` (the `In` query behind `admin/ops.rs:78`), `assign(ctx, user_id, role, assigned_by) -> Result<Assigned>` where `Assigned::{Created, AlreadyAssigned}`, `remove`. `assign` is the single writer for `ensure_admin_role`, `admin/iam.rs:343-376` and nothing else (2.2.3).

### 2.7 Auth credential model

Recommendation: make `AuthServiceImpl` verify the credential production issues, and delete the branches nothing issues.

- `crypto.rs` extracts `verify_access_token(ctx, token, secret, expected_iss) -> Option<AccessClaims>` from `extract_auth_meta` (`crypto.rs:51-145`: signature, `type == "access"`, issuer, blocklist, `auth_version`); the pipeline calls it and sets the meta as today.
- `extract_creds` becomes: Bearer that verifies as an access JWT -> `Creds::Jwt(sub)`; any other Bearer -> `Creds::Pat(hash)`; no Bearer -> `Unauthorized`. The secret and issuer come from `ctx.config_get(JWT_SECRET_KEY)` (the pattern at `csrf.rs:181`) and `helpers::expected_issuer`. `Creds::Session`, `session_cookie_from`, and the `wafer_session` cookie name are deleted; `require_user` on `Jwt` runs `ensure_active` and returns `UserId(sub)`.
- Why route rather than stub: the upstream typed client exists (`wafer-core/src/clients/auth.rs:47-82`) and the block is registered with `info_extras: grants` and `init` (`service_blocks/auth.rs:21-32`), so it stays registered either way; a stub that returns `Unauthorized` for the credential every request carries is a trap for the first caller. Why not read `msg.user_id()` instead: I could not verify that inbound `auth.*` meta is stripped before `extract_auth_meta` runs, so trusting forwarded meta inside the service is not something this spec can assert is safe; verifying the token is self-contained.
- The sessions table stops being a credential store (2.8). `tests/auth/service_require_*.rs` are rewritten to mint an access JWT with the test crypto service.

### 2.8 Session-row model (B12)

A session row is a login family, not an access token. Auth migration 012 replaces the table: `wafer_run__auth__sessions (family TEXT PRIMARY KEY, user_id, auth_method, created_at, last_used_at, expires_at)` with the user index; existing rows are 30-day UX rows keyed by hashes of expired tokens and are dropped with the old table. `SessionRow` gains `family` and `auth_method`, loses `token_hash`.

- `issue_tokens_and_cookie` with `family: None` inserts one row (`family = issued_family`, `expires_at` = the refresh row's `expires_at`); with `Some(family)` (rotation) it calls `sessions::touch(family, new_expires_at)`. One row per device, touched ~48 times a day instead of inserted.
- Logout deletes the caller's family's row when the refresh JWT is presented and, as today, revokes every refresh row for the user (`logout.rs:30`); this spec keeps that all-devices semantics and deletes all of the user's session rows with it, so the list and the tokens agree. Per-device logout is the userportal revoke: `DELETE /b/userportal/sessions/{family}` calls `tokens::revoke_family` then `sessions::delete(family)` and propagates both, so revoking a device actually signs it out (today it removes the list entry only).
- The current-session badge needs the family on the request. `generate_tokens` puts `family` on the refresh JWT (`auth/mod.rs:612-616`); whether the access JWT carries it I could not confirm from the excerpt read, so the PR adds a `family` claim to the access token if absent and `current_session_hash` (`userportal/pages/sessions.rs:59-66`) reads it from the verified meta.
- Session expiry equals refresh expiry. `SESSION_LIFETIME_DAYS` (`config.rs:22`) becomes the refresh TTL's source and its default changes from 30 to 7 so refresh validity is unchanged (`REFRESH_TOKEN_TTL_SECS`, `auth/mod.rs:38`, is deleted). Decision 5.2.
- Sweepers. `auth/maintenance.rs::sweep(ctx) -> SweepResult` calls `sessions::delete_expired`, `tokens::delete_expired` (new), `jwt_blocklist::delete_expired`, `oauth_pkce::delete_expired`, each rewritten over `db::delete_by_filters_count` (`wafer-core/src/clients/database.rs:570`) instead of list-then-delete. It runs in two places that exist on every platform today: throttled from `issue_tokens_and_cookie` on a fresh family (at most once per hour, the throttle stamp kept in a `platform_state::variables` row the way tickets keeps its singleton), and behind a `auth.maintenance` message kind mirroring `tickets/mod.rs:326` for an operator or a future cron. A Worker `scheduled` handler and `[triggers] crons` in the generated wrangler config are adapter work and are recorded for Phase 4; nothing in Phase 2 depends on them.

## 5. Decisions (taken; the reasoning is kept for the record)

**5.1 Credential model.** Recommend 2.7 (verify the access JWT inside `AuthServiceImpl`, delete the session-cookie branch, keep PAT and bootstrap-token). Evidence: zero `auth@v1` callers in impresspress or wafer-run (1.7); `wafer_session` is issued nowhere; PATs are inserted nowhere in production; the doc claim at `auth_ui/mod.rs:6-13` is false today. The alternative, deleting the `require_*` bodies to fail closed, leaves a registered service that rejects the one credential every request carries. Cost of the recommendation: one shared verify function and rewriting three integration tests.

**5.2 Session model and lifetime.** Recommend 2.8: one row per refresh family, touched on rotation, deleted on logout and revoke, expiry equal to the refresh row's. The open sub-point is the TTL: today refresh validity is a 7-day constant and the UX row is 30 days from a declared config var nobody else reads. Recommendation: `SESSION_LIFETIME_DAYS` drives the refresh TTL and its default becomes 7, preserving behaviour; raising it is a product decision. The alternative (keep two lifetimes) keeps the row lying about when the device is signed out.

**5.3 B14.** Recommend deletion (2.9). The alternative, declaring `WAFER_RUN__AUTH__INTERNAL_SECRET` as a `_SECRET` config var plus a `Config` read grant in `auth_grants()`, is two lines of code and one line of snapshot, but it keeps a header-secret user-creation endpoint alive with no consumer and no test; it is easy to add back with the caller that needs it.

**5.4 Where the platform DDL lives.** Recommend keeping the three admin SQL files as they are this phase (2.1.3): the hash gate makes any byte change a pending migration on every deployment, and no prefix rename is possible without the D1 data-migration path. The alternative, moving `variables`/`block_settings`/`wrap_grants`/`request_logs`/`user_roles` DDL into `platform_state/migrations/` now, forces a bless on `impresspress/admin` everywhere for no behavioural gain. Recorded for Phase 4 alongside the prefix rename.

**5.5 `messages_schema.rs` before Phase 4.** It can go now. The only consumer is `llm/pages.rs`; the replacement is the `call_block` path the same block already uses; no upstream change is involved (`call_block` attribution and Rule 3 are current wafer-run behaviour at `7d47e5e`).
