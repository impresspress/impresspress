## Decisions taken

These override the draft's recommendations wherever they differ. Section 5 is the reasoning that produced them and stays as the record.

1. **B11 — accept the finding.** It does not reproduce; `pending_review` and `pending` are values of two different columns, each consistent. Close it with a regression test pinning that the two columns are distinct and each round-trips, and fix the real residue: `ApprovalStatus`'s five variants describe the product column while the enum is bound to `SellerAccount`, where only two are reachable. No wire change. The review report's B11 row becomes "not reproducible; closed by test" rather than being deleted.
2. **Money — the column rename is deferred; the correctness half is done now.** Draft PR 7 (migration 021, dual write, wire rename) is dropped; draft PR 8 is kept and expanded — unify the two decimal parsers into `money::Decimal` with `to_minor(currency)`, and stop `total_cents`/`amount_cents` and `user_id`/`buyer_user_id` being published twice, so the hand-sync drift risk goes without a migration. The stored values are already correct minor units, so `_cents` is a misleading name rather than wrong data, while the two parsers disagreeing is a live correctness bug. See 2.3, which keeps the staged plan under a "deliberately deferred" heading.
3. **`errors.rs` — keep and shrink.** It is the only producer of the `error.code` the SDK reads, so it stays. `status_code()` is deleted (no callers, and it says 413 where 429 ships). The 847 `err_*` sites are **not** migrated; that is its own phase, and saying so here is part of the work.
4. **`get_bool` lives in `config_vars.rs`**, not upstream. Upstream is Phase 4 and wafer-run is pinned.
5. **Truth table A (`1`, `true`, `yes`, `on`) wins**, because it is the superset: no deployment whose config works today stops working.
6. **`context_type` stays a `String`.** It is not a closed set.
7. **Messages' role becomes a full `EntryRole` enum owned by the messages block**, not an extra arm in llm's parser. B20 is precisely the bug stringly-typing produces — the block documents `agent`, llm replays it as a user turn. The enum is the fix; the arm is the shim.
8. **Sequencing — ten PRs** (section 4). The draft's eleven minus the money migration, with its PR 8 becoming PR 7 as expanded in ruling 2. The three T4 sweep PRs stay separate: error-swallowing is the theme with the most fail-open behaviour left in the tree, and it is why several Phase 0 bugs existed. They are not folded into the enum PRs, which already move snapshots.
9. **Third snapshot gate.** `dev.tools.json` embeds the products contract schemas and only regenerates under `--features block-dev`. Every PR that moves a products contract runs the block-dev snapshot pass and either shows that file's diff or states it is unchanged.

## Goal

A stored value that is one of a fixed set is a Rust enum with one definition; a failure is reported with the code that describes it. Concretely, when this phase is done:

1. No block writes or compares a bare string literal for a status, role or kind that its own `contracts.rs` already defines an enum for. `grep -rn '"pending_review"\|"not_started"\|"dead_letter"\|"assistant"' crates/impresspress-core/src/blocks --include=*.rs` finds hits only in `contracts.rs` doc comments, migrations and tests.
2. Every enum'd column has exactly one decode door. `contracts::enum_column` (`blocks/products/contracts.rs:1276`) and `repo::offers::wire_enum` (`blocks/products/repo/offers.rs:34`) collapse into one helper with an explicit empty-column policy, and each content block gets the same.
3. `crud::db_error` and `http::require_row` exist, and no handler hand-writes `if e.code == ErrorCode::NotFound { err_not_found(..) } else { err_internal("Database error", e) }`. The count of that shape drops from **62** to 0 outside the two helpers, and `PermissionDenied` no longer arrives at a client as 500.
4. `errors::ErrorCode::status_code()` is gone (it has zero non-test callers and disagrees with the mapping that actually runs), and `rate_limit::rate_limited_response` no longer emits a `"[code] message"` prefix.
5. `SELLER_APPLICATION_FEE_BPS`, `PLATFORM_COUNTRY` and every boolean config flag are read through one function each, with one truth table.
6. B20, B21, B22, B23 are closed by construction, each with a test that fails on this tree. B11 is closed as **not reproducible** with a regression test that pins why (1.8).
7. Both snapshot gates plus `dev.tools.json` are byte-identical for every PR except the ones section 3 names, and each of those diffs is listed line by line in its PR.

## Why

The review's themes hold, but Phases 1 and 2 moved most of the evidence and closed some of it. What is left is sharper than the review describes in two places and much larger in one.

- **Products has already done half the enum work.** `contracts.rs` carries 25 enums (`:35-1336`), `OrderStatus` and `ReconciliationStatus` are written *and* read as enums (`repo/purchases.rs:263, 306, 409, 1143-1150`; `contracts.rs:2312, 2324`), and route schemas derive from the contract types (`routes.rs:30-31` imports `request_schema_of`/`response_schema_of`). The review's "48 drifted schema literals" is closed. What remains is a short, specific list (1.1).
- **The error problem is 8× the review's estimate.** The NotFound→404 / everything-else→500 shape appears at **62 sites across 27 files**, 34 of them with the literal context `"Database error"`, and none of them re-checks `PermissionDenied` — so a WRAP row-guard denial reaches the client as `500 Internal server error (ref: …)`. `err_internal`'s `context` argument never reaches the wire (`wafer-block/src/response.rs:77-89`), so all 62 are client-indistinguishable.
- **The money rename is a published wire change, not a column rename.** All eight `_cents` columns live on one table, `impresspress__products__purchases` (`migrations/001_products_schema.sqlite.sql:76-77`, `005_commerce_v2.sqlite.sql:200-204`, `013_order_shipping.sqlite.sql:4`), but they are also published in `products.openapi.json` (`:5561-5783`), typed in the SDK (`packages/impresspress-js/src/services/extensions.service.ts:745-752, 792-797, 854-860`), asserted in `pipeline.rs:1549`, and asserted in both CI workflows (`ci.yml:1251`, `ci-main.yml:871`). And the migration runner re-runs the whole concatenated corpus on any hash change (`migration_helper.rs:166-221`), tolerating only a duplicate `ADD COLUMN` (`:193-212`), so a bare `RENAME COLUMN` bricks every later migration.
- **Two config keys have two truth tables each.** `WAFER_RUN_SHARED__ALLOW_USER_PRODUCTS` is `{1,true,yes,on}` case-insensitively at `products/stripe.rs:989,1318` (through `configured_bool`, `stripe.rs:558-563`) and exactly `"true"` at `products/handlers/dispatch.rs:24`. `IMPRESSPRESS__PRODUCTS__AUTOMATIC_TAX` is the same split (`stripe.rs:1165,2353` vs `pages.rs:995`). So a value of `"1"` opens the route guard and closes the money path, or the reverse.

- **There was a 400-guard on `role` and it was deliberately removed.** `messages/rest.rs:529-558` is a regression test locking in that `assistant` and `system` must be *accepted*. Any enum must therefore include `assistant`, and the PR that tightens `role` has to reconcile with that test rather than delete it.

### 1.4 The error model

`errors.rs` (256 lines) exports `ErrorCode` (24 variants, `:4-42`), `as_str` (`:48-75`), `status_code` (`:80-111`), `Display` (`:114-118`), `error_response` (`:130-135`) and `pub(crate) impresspress_error_code_to_wafer` (`:138-172`, called from outside the module at `rate_limit.rs:299`).

- `status_code()` has **zero non-test callers** (exhaustive grep; the other `status_code()` hits in the repo are `resp.status_code()` on HTTP responses). It also disagrees with the mapping that runs: `QuotaExceeded | FileTooLarge => 413` (`errors.rs:102`) while the same two map to `ResourceExhausted` (`:160-162`) → **429** (`wafer-block/src/http_codec.rs:281`, reached via `resolve_error_status`, `:303-305`). `errors.rs:205-206` pins the unreachable 413.

## 2. Design

### 2.1 Status, role and kind enums

**2.1.1 One decode door per crate, in `util.rs`.** `enum_column` and `wire_enum` collapse into two functions beside `RecordExt`:

```rust
pub fn enum_column<T: DeserializeOwned>(record: &Record, column: &str) -> Result<T, WaferError>;
pub fn enum_column_or<T: DeserializeOwned>(record: &Record, column: &str, empty: T) -> Result<T, WaferError>;
```

`enum_column` keeps `contracts.rs:1276-1287`'s behaviour (unknown value → `Internal`, naming the row and column). `enum_column_or` is the `wire_enum` case, but takes the fallback as a **typed variant** rather than a string, so the fallback cannot itself be a value the enum does not define. `products/contracts.rs:1276` and `products/repo/offers.rs:34-43` delegate; the content blocks call it directly.

**2.1.2 Where each enum lives.** Each block's own `contracts.rs`, matching the existing convention — no shared enum module. The exception is `EntryRole`, which is owned by `messages/contracts.rs` because messages owns the column; llm converts (2.1.5).

**Wire values:** `assistant` wins over `agent`, because `assistant` is what llm has been storing and what `ChatRole` already spells, and `agent` survives as a deserialisation alias so existing rows and existing clients keep working. No stored row is rewritten.

**2.1.6 What moves in the published schema.** Three categories, and each PR states which it is in:

- Replacing a `String` field that already carries `#[schemars(extend("enum" = [...]))]` with the real enum type: the generated schema is the same `{"description", "enum", "type"}` object (compare `approval_status` at `products.openapi.json:525-535` with the real-enum `mode` at `:4846`-adjacent, `{"enum": ["payment","subscription"], "type": "string"}`). **Expected byte-identical**; the PR proves it by regenerating and showing no diff.
- Replacing a bare `String` field with an enum: adds an `enum` array where there was none (`tax_behavior`, `usage_type`, `SellerAccount.status`, every messages field). **Moves the snapshot**, tightening a published contract that was already documented in prose. Each such line is listed in the PR body.
- `Option<Enum>` fields: `recurring_interval` currently renders `{"type": ["string","null"]}`. schemars renders an optional enum differently; the PR must show the produced shape rather than assume it.

**2.1.7 Requests get tighter, and one existing test says how far.** Typing a request-body or query field rejects values the handler previously accepted and stored. For messages that is the point — nothing validates `role` today (`messages/rest.rs:170-171`) — but it is a behaviour change: `POST /b/messages/api/contexts/{id}/entries` with `"role": "bot"` moves from 201 to 400.

`messages/rest.rs:529-558` is the constraint. It exists because a previous commit added a 400-guard on `role` and it was removed; the test now pins that `assistant` and `system` **must be accepted**. `EntryRole` satisfies it as written (both are variants), so the test survives unchanged and is the reason `assistant` — not `agent` — is the canonical spelling. The PR extends it with the `agent`-accepted case rather than replacing it.

`role`'s `#[serde(default)]` (`contracts.rs:63`) currently yields `""`, and `llm/routes/chat.rs:72` drops empty-role entries from model history — so today the messages block's own default makes an entry invisible to the LLM. It becomes `#[serde(default = "EntryRole::user")]`: an omitted `role` stores `"user"` instead of `""`, which is a behaviour change and a strict improvement. Existing `""` rows keep failing to parse; `enum_column_or(record, "role", EntryRole::User)` reads them as user turns, which is what `chat.rs:43` intended and `:72` accidentally prevented.

The list filters (`messages/service.rs:225-243`) parse the same enum and answer 400 on an unknown filter value rather than silently returning an empty page.

### 2.2 The error model

**2.2.1 `From<ErrorCode> for OutputStream`.** The one `From` impl orphan rules allow:

```rust
impl From<ErrorCode> for wafer_run::OutputStream { ... }   // in blocks/errors.rs
```

It is `error_response(code, code.default_message())` — a message table beside `as_str`. `error_response(code, message)` stays for the sites that need a specific message. This lets `?` carry an `ErrorCode` out of a handler and lets a match arm read `ErrorCode::NotFound.into()`.

**2.2.2 `crud::db_error`.** One function replacing the four copies inside `crud.rs` and the 58 outside it:

```rust
pub fn db_error(e: WaferError, not_found: &str, context: &str) -> OutputStream
```

`NotFound` → `err_not_found(not_found)`; **`PermissionDenied` → `err_forbidden`** (the behaviour fix: a WRAP denial stops being a 500); `ResourceExhausted` → the 429 the wafer mapping already gives; everything else → `err_internal(context, e)`. `crud.rs:119-125, 161-167, 181-187, 232-235` become one call each; `list_page:106-108` and `create_record:143-148` call it with no 404 case through a `db_error_internal` sibling.

**2.2.3 `http::require_row`.** For the 38 repo functions now returning `Result<Option<_>>`:

```rust
pub fn require_row<T>(row: Option<T>, not_found: &str) -> Result<T, OutputStream>
```

so a handler reads `let user = require_row(repo::users::find_by_id(ctx, id).await.map_err(db_error_for)?, "User")?;`. It lives in `http.rs` beside `redirect`, not in `crud.rs`, because it has nothing to do with the generic-table helpers.

**2.2.4 `RepoError` folds into `WaferError`.** `auth::repo::RepoError` (`auth/repo/mod.rs:36-44`) discards the wafer code, which is exactly what 2.2.2 is trying to preserve. The 15 auth repo functions return `Result<_, WaferError>` like the products and dev repos, and `RepoError` is deleted. This is the single largest mechanical part of the error PRs and is why auth gets its own PR.

**2.2.5 `errors.rs`.** `status_code()` and its test (`errors.rs:80-111, 178-215`) are deleted: zero callers, and its one substantive claim (413 for quota) contradicts the 429 that actually ships. `ErrorCode`, `as_str`, `Display`, `error_response` and the new `From` stay; `impresspress_error_code_to_wafer` becomes `pub(crate)` still but gains a doc line naming `http_codec::error_code_to_http_status` as the authority. See decision 5.3 for the alternative.

**2.2.6 `rate_limit::rate_limited_response`.** `rate_limit.rs:296-312` drops the `"[{}] "` prefix and attaches the detail code through `WaferError::with_detail_code(ErrorCode::RateLimitExceeded.as_str())`, keeping its hand-built `Retry-After` meta. That is a wire change on a 429 body: `message` loses the bracket prefix and the response gains a `code` field the SDK already reads (`http-client.ts:167`). No test pins the current body.

**2.2.7 The 51 empty-id guards.** Every `if id.is_empty() { err_bad_request("Missing X ID") }` becomes `crud::path_id(msg, "X")?`. `crud.rs:44-47` argues the guard is unreachable through the route table; the PR keeps `path_id` (it is the documented door) and deletes the copies.

### 2.3 Money

**Ruling 2 splits this item in two.** The correctness half — one decimal parser and one published source of truth for the duplicated columns — is done in this phase, as PR 7 (2.3.6, 2.3.7). The column rename and the wire rename are **deliberately deferred** and are not in this phase; 2.3.1–2.3.5 are kept below, unchanged, as the plan that a later release would execute.

The reason for the split: the stored values are already correct minor units (`repo/purchases.rs:265-272` writes `snapshot.amounts.total_minor` into `total_cents`), so `_cents` is a misleading *name* on correct data. The two decimal parsers disagreeing (1.5, last bullet) is a live correctness bug on the money path. A live-data migration plus a published wire rename, run unattended, is the worst risk-to-value ratio in the programme; the parser unification and the duplicate-column de-publication carry the same correctness benefit for a tenth of the diff and no migration.

#### 2.3.a Deliberately deferred: the `_cents` → `_minor` column and wire rename

Not in this phase. What it would take, kept so it can be scheduled as its own release: 2.3.1–2.3.5 below, in full — an additive migration `021` (Stage A), a dual-write release (Stage B) that also moves every published wire name, the SDK and both CI `information_schema` assertions, and a later `022` that drops the old columns (Stage C). The blocking facts are that `apply_if_blessed` re-runs the whole concatenated corpus on any hash change and tolerates only a duplicate `ADD COLUMN` (`migration_helper.rs:193-212`), that no `RENAME COLUMN`/`DROP COLUMN` precedent exists anywhere in the repo, and that the seven names are published in `products.openapi.json`, `dev.tools.json`, the SDK and two CI workflows. Nothing in this phase makes that work harder: PR 7 leaves every column name exactly as it is.

**2.3.1 What is renamed.** `total_cents → total_minor`, `subtotal_cents → subtotal_minor`, `discount_cents → discount_minor`, `tax_cents → tax_minor`, `shipping_cents → shipping_minor`, `platform_fee_cents → platform_fee_minor`, `refunded_total_cents → refunded_total_minor`. `amount_cents` and `user_id` are **dropped**, not renamed: `amount_cents` has one reader publishing a field documented as legacy (`contracts.rs:2165, 2630`), and `user_id` is a mirror of `buyer_user_id` with a divergent read set (1.5).

Note that six of the seven new names already exist as `_minor` columns on **other** tables (`line_items`, `refunds`), which is the point — after this, one name means one thing.

**2.3.2 Stage A — migration 021, additive only.** `021_purchase_amount_columns.{sqlite,postgres}.sql`:

```sql
ALTER TABLE impresspress__products__purchases ADD COLUMN total_minor INTEGER NOT NULL DEFAULT 0;
-- … six more ADD COLUMNs …
UPDATE impresspress__products__purchases SET total_minor = total_cents, … WHERE total_minor = 0;
```

Every statement is re-run-safe by the two mechanisms the repo already relies on: `ADD COLUMN` duplicates are tolerated (`migration_helper.rs:193-212`) and the backfill `UPDATE` is idempotent because Stage B writes both columns, so re-running it copies a value onto itself. The postgres file uses `ADD COLUMN IF NOT EXISTS` as `005_commerce_v2.postgres.sql:171-175` does. **No `RENAME COLUMN` and no `DROP COLUMN`** — neither is tolerated on re-run and neither has a precedent in this repo (1.5).

The `WHERE total_minor = 0` guard is what makes the backfill safe on re-run *and* on a fresh database where the ADD COLUMN default already applies; a legitimately-zero order is copied 0 onto 0.

**2.3.3 Stage B — dual write, single read.** `repo/purchases.rs`'s two writers (`:265-272`, `:838-845`) write **both** spellings of each column. Every reader moves to `_minor`. This is the release that can be rolled back: an old binary against a new database still finds `_cents` populated.

**2.3.4 Stage C — contract, next release, not in this phase.** A `022` that drops the seven `_cents` columns plus `amount_cents` and `user_id`, and a PR that removes the dual write. It is out of scope here because a `DROP COLUMN` is not re-run-safe under `apply_if_blessed` either, and designing that (a `DROP … IF EXISTS` on postgres, a guarded sqlite path, or accepting a one-way migration behind `IMPRESSPRESS_RUN_MIGRATIONS`) is its own piece of work. Recorded in `RELEASE.md`'s Upgrade Notes, which 020 already established as the place for this.

**2.3.5 The wire.** Because every view is hand-projected (`contracts.rs:2619-2636`), the wire names are a *separate* decision from the column names. Recommendation (5.1): rename the wire fields in the same PR as Stage B, because leaving `total_cents` on the wire while the column is `total_minor` is precisely the "translation between representations" `CLAUDE.md` forbids. That makes Stage B a breaking API change and it must move together:

- `products.openapi.json`: seven property keys per order-shaped schema (`:5561-5783` and the three other order projections), plus the removal of `amount_cents` and `user_id`.
- `dev.tools.json`: the same schemas are embedded in the WebMCP tool manifest (`dev.tools.json:193-1168` carries the products contract schemas), regenerated with `UPDATE_DEV_TOOLS_SNAPSHOT=1` under `--features block-dev`.
- `pipeline.rs:1547-1550`: `refunded_total_cents` → `refunded_total_minor`.
- SDK `extensions.service.ts:734, 745-752, 792-797, 854-860`.
- `ci.yml:1251` and `ci-main.yml:871`: `shipping_cents` → `shipping_minor`.
- `products/pages.rs:2440, 3203, 3309, 3313, 3377, 3385-3389, 3768`.

#### 2.3.b In this phase (PR 7)

**2.3.6 `money::Decimal`.** The dead `money::parse_amount_minor` (`money.rs:41-94`) and the live `offer_pricing::Decimal` (`:58-111`) become one type in `money.rs`: `Decimal` moves there, keeps its scale-9 cap and its exact arithmetic, and gains `to_minor(currency) -> Result<i64, String>` built from `parse_amount_minor`'s exponent logic (`money.rs:63-93`) — so the currency exponent finally reaches the pricing path. `parse_amount_minor` becomes `Decimal::parse(s)?.to_minor(currency)`. The sign difference is resolved explicitly: `Decimal::parse` keeps accepting negatives (refund and adjustment paths need them) and `to_minor` rejects them unless a `to_signed_minor` is asked for. `offer_pricing.rs` imports the type instead of defining it.

**2.3.7 One published source of truth for the duplicated columns.** The two duplicate pairs are a *publication* problem before they are a *storage* problem, and the publication half needs no migration because every view is hand-projected (`contracts.rs:2619-2636`).

- `PurchaseView.amount_cents` (`contracts.rs:2165`, fed by `:2630`) is removed from the view. **This moves `products.openapi.json` and `dev.tools.json`** (two removed properties per order-shaped schema) and the SDK's three order interfaces (`extensions.service.ts:734, 745-752, 792-797, 854-860`), so PR 7 carries a reviewed diff for all three. ### 2.4 One boolean truth table

**2.4.1 `config_vars::get_bool`.** In `config_vars.rs` beside `shared_var`/`var_in`, not in `wafer_core::clients::config` (which is upstream — decision 5.4):

```rust
pub async fn get_bool(ctx: &dyn Context, key: &str, default: bool) -> bool
```

Reads through `config::get_default(ctx, key, if default {"true"} else {"false"})` and applies **table A**: trim, ASCII-lowercase, `matches!(v, "1" | "true" | "yes" | "on")`. Table A is chosen over table B/C because it is the superset — every value that is true under B or C is true under A, so no deployment that works today stops working. It is also what `products/stripe.rs:558-563` and `tickets/config.rs:201-206` already implement.

**2.4.2 Call sites.** All of table A (`stripe.rs:558-563` deleted, `tickets/config.rs:201-206` deleted, `tickets/service.rs:620-631` deleted), all of table B (`auth/mod.rs:394-397`, `auth_ui/api/{signup,login,refresh}.rs`, `auth_ui/oauth/{start,callback}.rs`) and all of table C (`auth_ui/pages/{login,signup}.rs`, `products/handlers/dispatch.rs:23-25`, `products/handlers/product.rs:836-844`, `products/pages.rs:989-995`) call `get_bool`. **2.4.3 The render half.** `ui/settings_form.rs:117` (`checked[value == "true"]`) uses the same predicate, so a toggle set to `1` from the environment draws as on.

**2.4.4 Form and DB coercion stay separate.** `tickets/public.rs:624-631` and `vector/contracts.rs:206-207` read *form* fields and `admin/mod.rs:718-721` reads a form field; they get a sibling `form_bool` with the same table (an HTML checkbox posts `on`). `auth/repo/mod.rs:86-93`, `tickets/service.rs:653-660` and `llm/schema.rs:147-154` decode *database* values, where `Bool` and `Number` are the real cases; they are unified separately onto `RecordExt::bool_field`, which `auth/repo/users.rs:148-151` already documents as the round-trip for both backends. `llm/schema.rs:147-154`'s fail-open default (unrecognised → `true`) is preserved deliberately or changed deliberately, not by accident — it decides whether a provider is enabled.

## 5. Decisions

Ruled on 2026-09-06; see "Decisions taken" at the top for what was decided. This section is the reasoning that produced those rulings and is kept unedited as the record. Where a recommendation below differs from a ruling — 5.1 (money) is the only one — the ruling governs.

**5.1 Is the money rename worth doing in this phase?** *Recommend yes, as Stage A + B only (2.3.2–2.3.5), with Stage C deferred.* Evidence for: the name is provably wrong (`money.rs:24-33` supports 0- and 3-decimal currencies, and the published description of `total_cents` already says "in minor units", `products.openapi.json:5783`); six of the seven target names already exist on sibling tables, so the codebase currently uses two names for one concept *within one block*; and the two duplicate pairs (`amount_cents`, `user_id`) are a live correctness risk, not just a naming one, because their read sets differ (1.5). Evidence against: it is the only item in the phase that touches live rows, it breaks a published API and the SDK, and it costs a migration in a runner with no rename precedent. The staging removes the data risk entirely — Stage A only adds columns and copies values, both re-run-safe — and defers the only irreversible step. **If the ruling is "not now", the fallback is to do 2.3.6 (`Decimal`) and drop `amount_cents`/`user_id` from the *views* alone, leaving the columns; that closes the correctness risk for a tenth of the diff.**

**5.2 Does B11's fix change the wire or the code?** *Recommend neither: B11 is closed as not reproducible.* Evidence: `pending_review` and `pending` are values of two different columns, each written, read and published consistently (1.8, with eight cited sites). The PR that closes it adds a regression test asserting the invariant the code maintains by hand — `status == pending_review` ⟺ `approval_status == pending` at `handlers/product.rs:1016-1023` — and binds `ProductView.approval_status` to `ApprovalStatus` so the two vocabularies stop being adjacent bare strings. That is a code change with an expected byte-identical schema (2.1.6, first category). No wire value changes.

**5.3 Should `errors.rs` become the single error constructor, or be deleted?** *Recommend: keep it, shrink it, and do not migrate the 847 `err_*` sites to it.* Evidence: `errors::ErrorCode` is the only thing that produces the `error.code` detail meta the SDK reads (`http-client.ts:167`, `error.ts:22`); `err_*` produce none. Deleting `errors.rs` would drop a machine-readable code from 36 auth responses that clients may switch on. Migrating the other way — 847 sites onto `ErrorCode` — is a phase of its own and would need a detail code invented for each. So: `errors.rs` keeps `ErrorCode`, `as_str`, `Display`, `error_response` and gains `From`; it loses `status_code()`; `err_*` stay the default for everything that does not need a fine-grained code. The one rule added is that no handler builds a `WaferError` by hand (the `rate_limit.rs:304` shape) — that is what 2.2.6 fixes. **The alternative worth naming:** give `err_*` an optional detail code upstream and delete `errors.rs` entirely — that is a wafer-run change and belongs in Phase 4's upstream list.

**5.4 `config_client::get_bool` or `config_vars::get_bool`?** *Recommend `config_vars::get_bool` (2.4.1).* `config_client` is an alias for `wafer_core::clients::config`, so the review's phrasing implies an upstream change; the brief puts upstream work in Phase 4. A local helper reads the same `get_default` and costs nothing. **Recorded for Phase 4's upstream list:** `config::get_bool` in `wafer-core`, at which point the local one becomes a re-export.

**5.5 Which truth table wins?** *Recommend table A (`{1,true,yes,on}`, trimmed, case-insensitive).* It is the superset, so no working deployment breaks; it is already what the two most-used helpers implement; and the admin UI only ever writes `true`/`false` so the widened set is only reachable from env/`.env`, where `1` is the conventional spelling. The alternative — table C, exactly `"true"` — would silently *disable* features for anyone using `=1` today, which is the same class of bug as the one being fixed.

**5.6 Does `StripeClient` need to expose the status code?** *Recommend yes, as `meta` on the error rather than a new return type.* `stripe_catalog_get` needs 404-means-absent (`stripe.rs:1394-1396`) and three sites log the raw status (`:1223-1229`, `:2376-2382`). Attaching `resp.status` to the `WaferError` meta keeps `request_json`'s signature and is the smallest change; the alternative (a `StripeError` struct) is cleaner but is really part of Phase 4's `stripe.rs` split.

**5.7 The `ContextType` variant set.** *Recommend leaving `context_type` a `String`.* `messages/contracts.rs:32` documents "conversation, task, notification, **etc.**" — unlike `role` and `kind`, there is no closed set, and the block's own code only ever tests one value (`pages.rs:184, 263`, both `"conversation"`). Typing a field whose documented set ends in "etc." is how a 400 arrives for a value that was always legal. The alternative, an enum with an `Other(String)` escape, buys nothing: it validates nothing and still moves the snapshot. If someone can name the closed set, this flips.

**5.8 How far to tighten the messages request bodies.** *Recommend: type `role` and `kind`, keep the removed 400-guard removed in spirit.* `messages/rest.rs:529-558` exists because a `role` guard was added once and reverted; the enum satisfies that test as written because `assistant` and `system` are variants. But it does mean `POST .../entries` with an unrecognised `role` moves from 201 to 400, which is a wire behaviour change on a block the review calls the cleanest in the repo. The reason to do it anyway is B20: llm replays whatever string is there, and `agent` — the only value the block's own composer offers — is currently replayed as the user. **The alternative** is to fix `role_from_str` alone (add an `"agent" => Assistant` arm) and leave the column untyped; that closes B20 for a two-line diff and no snapshot movement, and leaves the underlying "any string is a role" problem for later. Say which, because it changes PR 3's size by roughly half.
