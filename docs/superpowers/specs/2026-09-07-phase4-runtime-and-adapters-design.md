## Decisions taken

These are the rulings of 2026-09-07. They override the draft's recommendations wherever they differ; section 5 is the reasoning that produced them and stays as the record. Sequencing stands as drafted: nine PRs, three producer, the pin bump alone as PR 4, five consumer.

**5.1 Browser adapter — accepted as recommended.** Full `impresspress-core` dependency plus the targeted vector deletions; do NOT rewrite `vector/sql.rs` onto `VectorIndexSchema`. That rewrite needs an upstream storage variant AND an OPFS data migration with no CI to catch a mistake, which is not a trade to make unattended. The streaming and SSRF gaps are live defects and are the point of the PR.

**5.2 Platform DDL move and prefix rename — accepted, both stay deferred, together.** Moving the DDL alone would leave `platform_state/migrations/` creating `impresspress__admin__*` tables, which buys nothing and costs a bless on every deployment. Note in the spec that this is now the SECOND deferral and write down exactly what unblocks it: a D1 data-migration path plus a re-run-safe rename. It should not slide a third time without someone deciding it on merit.

**5.3 Upstream items with no consumer — accepted, skip all five.** Adding API to a shared library that this consumer does not use is speculative work, and it lands on every other consumer of that library too. The "a second pin bump is expensive" argument is real but it is an argument about OUR convenience, not about the producer's interface. If a later phase needs `Filter::eq` or `find_by_field`, that phase bumps the pin for it. Record the five in the spec as consciously skipped, with the counted benefit each would have had, so the next person does not re-derive it.

**5.4 The OpenAI codec lives in `impresspress-core` — accepted, overruling the review.** The producer has no OpenAI code and states a no-conversion-layer design position; pushing a vendor codec into it to satisfy a tidiness argument would be us imposing our shape on a library we do not own.

**5.5 The Cloudflare request path runs `seed_after_admin_init` — accepted.** It is skipped by accident, which is a bug, not a design choice.

> **5.5 AMENDED 2026-09-07, after PR #38's review. The amendment replaces the ruling above; do not implement the original.**
>
> The original ruling's premise was false. It said the request path "already performs" the block-settings load-and-seed inline, so passing `CfBootHooks` "removes a copy rather than adding work". The request path performs a read-only `load` plus republish, not a `load_and_seed`; `platform_state/block_settings.rs:213-221` states the invariant that it must stay physically write-free so a cold runtime cannot invalidate itself. Wiring the seeding hook in converts a write-free path into a writing one under `InitPolicy::Strict`, with three traced failure modes: missing tables 500 every request, a successful seed bumps the KV config generation and forces a full dynamic rebuild fleet-wide, and concurrent isolates race a UNIQUE insert.
>
> The three Cloudflare paths are not interchangeable. The deploy path keeps the full `CfBootHooks` with seeding, because seeding is a deploy-time mutation. The two dynamic request paths get a read-only hook: `load` plus republish, no seed and no generation bump. The prepared hydration path keeps its written no-op hook.

**5.6 B9 — accepted.** Keep the provider routes declared and answer 501, since omitting them erases them from the snapshots (the info set is built with the no-op provider admin). Add the Cloudflare passthroughs but do NOT put them in `default` or `full` until someone has measured the wasm size; say in the PR body that the measurement is what gates it.

**5.7 The KV cache keeps its refuse policy — accepted.** The forwarder macro is what makes a decorator enumerate every operation, which is the structural half; refusing is the safe half. Keep both.

**5.8 CLI typestate deploy and the `deploy.rs` split — accepted, deferred.** The two loudest CLI findings are already closed and the deploy path has no CI coverage at all. Refactoring an untested deployment path unattended is the wrong risk. Record it for a phase where someone can exercise a real deploy.

**Also binding, from section 3.** PR 4 must force on the two path-filtered wasm-test jobs; PRs 5 to 9 each re-run the wasm AND CLI lanes, because the pin moved under them; and the nine unpinned `git clone wafer-run` sites in `ci.yml` get NAMED in PR 4's body as a hazard, not fixed there.

## Goal

One post-`build()` lifecycle, one place that fills the runtime's config surfaces, one copy of every adapter helper, and no runtime capability chosen by `cfg`. Concretely, when this phase is done:

1. `grep -rn 'strict_init_all_blocks\|init_all_blocks\|post_start' crates/` finds them only inside `builder/boot.rs`. `impresspress-cloudflare` and `impresspress-web` and `impresspress/src/cli/server.rs` each call `builder::boot(wafer, hooks, policy)` and nothing else. `deploy_init` is `boot` with `InitPolicy::Reported`, not a second function.
2. Exactly one function writes both the `ConfigService` map and the `set_config_snapshot` map, and it is in `impresspress-core`. `grep -rn 'set_config_snapshot' crates/` finds one non-test call site.
3. No file in `crates/impresspress-cloudflare/src/` exceeds 900 lines (`lib.rs` is 2,077 and `runtime_cache.rs` 1,851 today). `get_or_build` and `get_or_build_prepared` share one build-and-init path; `apply_db_wrap_grants` is not something a caller can forget.
4. `crates/impresspress-browser/Cargo.toml` names `impresspress-core`, and `grep -rn 'is_streaming_content_type\|collect_buffered_with_prelude\|matches_filter\|RRF_K\|fn pack_vector_blob' crates/impresspress-browser/src/` returns nothing.
5. B9, B18, B19, B25 and B26 are closed by construction, each with a test that fails on this tree. B5, B6 and B7 are recorded as **already closed** by Phase 0/2 with the evidence in 1.3, and the review's rows are updated rather than deleted.
6. Both snapshot gates plus `dev.tools.json` are byte-identical for every PR except the ones section 3 names, and each of those diffs is listed line by line in its PR.
7. `cloudflare`, `web` and CLI declare the same `block-*` set, or a test names the difference and why. The wasm32 middleware hand-list (`builder/registration.rs:219-242`) is gone.
8. The Worker has a `scheduled` handler and the generated wrangler config has `[triggers] crons`; `blocks::auth::maintenance::sweep` runs from it.
9. `tests/wafer_pin_surface.rs` names every producer API this phase adds, so a wrong pin fails by name.

## Why

Phases 0-3 moved or closed a large part of what the review saw here. What is left is smaller and sharper than the review describes in three places and larger in one.

- **The lifecycle problem is worse, not better: there are four orderings, not three.** `builder::boot` (`impresspress-core/src/builder/boot.rs:115-138`) seals, inits admin *tolerantly*, runs the seed hook *fatally*, `init_all_blocks()` *tolerantly*, `post_start`. `deploy_init` (`impresspress-core/src/deploy_init.rs:56-121`) hand-rolls a third init loop so it can report per block, and its seed-hook failure is captured, not fatal. The Cloudflare request path has **two** further orderings: the stored/transient dynamic builds (`impresspress-cloudflare/src/runtime_cache.rs:806-822`, `:1062-1072`) do `apply_db_wrap_grants → seal → strict_init_all_blocks → post_start`, and the prepared hydration (`:889-949`) does the same **without** `apply_db_wrap_grants`. None of the three CF copies runs `seed_after_admin_init` at all — no `BootHooks` value exists on that path. `boot.rs:60-63` still claims "the two stateless targets (Cloudflare, browser) collapse to a hook impl"; that is true of the browser (`impresspress-web/src/runtime_factory.rs:535-537`) and false of Cloudflare, which the CF file itself says at `impresspress-cloudflare/src/lib.rs:1831-1833` ("the per-isolate cache seals without a boot funnel"). `CfBootHooks` (`lib.rs:1834-1864`) is constructed at exactly one site, `lib.rs:957`, inside `/_deploy/init`.
- **The config surfaces are filled in four places, not three,** and only one key is common to all of them. Native `impresspress/src/cli/server.rs:209-257` (+ snapshot at `:306`, + a third surface `StaticConfigSource` at `:286`) still carries the comment "Both must carry the same data" at `:234-240`; CF `impresspress-cloudflare/src/lib.rs:1172-1237` (+ `:1325`) *deliberately* diverges the two (request config reaches the service map and not the snapshot, `:1228-1233`); browser `impresspress-web/src/lib.rs:162-201` adds a `RUNTIME_KIND_CONFIG_KEY` no other target sets; and `request_services_for_dispatch` (`lib.rs:1369-1434`) rebuilds the map a fourth time per warm request with a *remove* branch that exists nowhere else (`:1389-1411`). Only `BLOCK_SETTINGS_CONFIG_KEY` appears in all four.
- **The browser adapter is 6,207 lines of which ~1,900 are re-implementations of code already in `impresspress-core` or in the pinned producer,** and two of them are wrong. `convert.rs:456-465` decides to stream on content-type alone, never consulting `streaming::wants_streaming` / the `resp.stream` marker (`impresspress-core/src/streaming.rs:52,108`), so a marked download that Cloudflare streams (`impresspress-cloudflare/src/convert.rs:114`) is buffered whole in the browser, with no cap (core's `MAX_BUFFERED_RESPONSE_BYTES` is `streaming.rs:67`; CF enforces it at `convert.rs:124,194-216`). `network.rs:30-67` has no SSRF gate although `impresspress-core/src/ssrf.rs:73` exists and CF uses it at `network_service.rs:55-60`. And the whole objection is already refuted by the build graph: `impresspress-web` (wasm32) depends on `impresspress-core` with `default-features = false` (`impresspress-web/Cargo.toml:75`) **and** on `impresspress-browser` (`:35`), so core is already in the browser bundle.
- **Three of the review's rows here are already fixed and must not be re-done.** B5 (browser CSP overwritten at step 12): `impresspress-core/src/flows/mod.rs:143-152` now merges consumer-declared CSP with the shared default via `merged(...)` (`:180-212`), `builder/registration.rs:499-508` threads `&self.block_configs` into `register_site_main`, and `IMPRESSPRESS_CSP` is live at `impresspress-web/src/runtime_factory.rs:549`. B6 (KV wrapper inherits `take_where`/`delete_where_count`): overridden at `impresspress-cloudflare/src/kv_cached_db.rs:428-454` with four regression tests (`:985-1024`). B7 (two WRAP-grant loaders): `impresspress/src/cli/server_config.rs` is 28 lines with no rusqlite; the single loader is `impresspress-core/src/platform_state/wrap_grants.rs:145-183`.
- **Five upstream items the review asked for are unnecessary or blocked, and one it did not ask for is already done.** `DbExec::run_batch` already exists with a sequential default (`wafer-core/src/interfaces/database/exec.rs:315-338`) and `DbExec::list` already batches count+select; the D1 override landed consumer-side at `impresspress-cloudflare/src/database.rs:341`, closing `docs/d1_statement_batching_producer_design.md`. `Block::info` as an associated fn is blocked by two receiver-dependent impls (`wafer-run/src/wasm/wasmi_loader/mod.rs:1016-1024` instantiates the guest; `wafer-core/src/service_blocks/auth.rs:22` embeds instance grants). Details in 1.1.

### 2.3 One `builder::boot` with an `InitPolicy`

`builder::boot` becomes:

```rust
pub enum InitPolicy { Tolerant, Strict, Reported }
pub enum GrantSource<'a> { Database(&'a Arc<dyn DatabaseService>), Plan(&'a [ResourceGrant]) }
pub async fn boot(wafer, storage_block, hooks: Option<&dyn BootHooks>, grants: GrantSource<'_>, policy: InitPolicy)
    -> Result<BootReport, RuntimeError>
```

Ordering is fixed for all four callers: `apply grants → seal → init admin → seed hook (if any) → init the rest → post_start`. The policy chooses only what a failure *does*: `Tolerant` warns (today's `boot.rs:125-127,134`), `Strict` fails closed (today's `strict_init_all_blocks`), `Reported` captures per-block outcomes into `BootReport` (today's `deploy_init.rs:94-110`). `BootReport` is `DeployInitReport` renamed; `Tolerant`/`Strict` callers ignore it. `deploy_init.rs` is deleted; `/_deploy/init` calls `boot(.., Some(&CfBootHooks), GrantSource::Database(&db), InitPolicy::Reported)`.

`GrantSource` is the point: `apply_db_wrap_grants` stops being a thing a caller can forget (`runtime_cache.rs:889-949` forgets it today). The prepared path passes `GrantSource::Plan(&plan.structure.wrap_grants)` and the compiler requires it. The CF request path passes `hooks: Some(&CfBootHooks)` — closing the silently-skipped `seed_after_admin_init` — with the seed made idempotent and cheap enough for the request path (it already is: `CfBootHooks` reads block settings and republishes, `lib.rs:1844-1861`), or `None` with a one-line justification per call site. **Ruling needed (5.5).**

## 5. Decisions (the draft's recommendations, kept as the record)

**5.1 How far the browser adapter goes.** Recommend the **full `impresspress-core` dependency plus targeted vector deletions, and explicitly NOT rewriting `vector/sql.rs` onto `VectorIndexSchema` in this phase.** Evidence for the dependency: `impresspress-web` is wasm32, already takes `impresspress-core` with `default-features = false` (`impresspress-web/Cargo.toml:75`) and already takes `impresspress-browser` (`:35`), so core is in the shipping bundle either way — the dependency adds zero wasm build risk and zero bytes for the only consumer that ships. `streaming.rs`'s own module doc names the browser as an intended consumer (`:1-28`), and the two defects it would fix (unstreamed marked downloads, no buffered cap) are live. Evidence for stopping short of the vector rewrite: `wafer_sql_utils::vector::VectorIndexSchema` is hard-wired to sqlite-vec `vec0` (`wafer-sql-utils/src/vector.rs:29,75`), the browser stores blobs, so adopting it *requires* upstream item 7a — four new branches in the producer's SQL builders — and the browser's tables are named `_vectors` where upstream names them `_vec`, so the change is a live data migration in the user's OPFS database with no migration path and no CI that exercises it. `matches_filter`, the inline RRF and the double flush path are deletable **without** any of that, and they are where the actual divergence risk is (a false-premise comment and two durability contracts). The alternative — targeted deletions with no core dependency — keeps `is_streaming_content_type` and the missing SSRF gate, which is the half that is a security and correctness gap rather than a tidiness one.

> **Correction (PR #40, merged).** Not zero bytes: **+28,332** on the
> `impresspress-web` bundle (+0.41 %). See the correction in 2.7. The ruling is
> unaffected — the bytes buy an SSRF gate, a streaming download path and a
> buffered-response ceiling — but the evidence as the draft stated it was wrong.

**5.2 The platform DDL move and the `impresspress__admin__` prefix rename.** Recommend **both stay deferred, together, as their own release.** Evidence: `platform_state/` already exists with five owners (`variables.rs:28`, `block_settings.rs:34`, `wrap_grants.rs:23`, `request_logs.rs:25`, `user_roles.rs:22`), so the *code* boundary Phase 2 wanted is done; what is left is the table names and the DDL files, and those two must move together or the result is `platform_state/migrations/001_*.sql` creating tables called `impresspress__admin__*`, which is a worse resting state than today. Moving the DDL alone is cheap and safe in isolation (`blocks/admin/migrations/001_admin_schema.sqlite.sql` is nine `CREATE TABLE IF NOT EXISTS` with no `DROP`, and `migration_helper`'s hash gate keys per block id, so a new `impresspress/platform` set is additive and idempotent on existing databases) — but it forces a `blessed_hash` bless on `impresspress/admin` for every deployment with no behavioural gain, and it buys nothing that the rename does not have to redo. The rename needs a real D1 data migration with no rollback, and nothing in Phase 4's remit depends on it. Counter-argument to weigh: this is the second phase to defer it, and deferring twice is how an item becomes permanent — if you want it, PR it as a tenth PR here doing *both* halves, not as a DDL move alone.

**5.3 The upstream items impresspress does not need.** Recommend **not doing items 1b, 2, 3, 10 and 13b**, and recording them in `wafer-run`'s `CHANGELOG.md` under a "wanted, unimplemented" note. Evidence per item: 1b (`after_mutation`) has no consumer because the KV wrapper deliberately *refuses* bulk writes on cached tables rather than invalidating (`kv_cached_db.rs:421-440`), and adding an invalidation hook would invite reversing a decision that already shipped with four regression tests; 2 and 3 target repo micro-patterns in `auth/` and `products/`, which Phases 2 and 3 already moved into `repo/` modules and which Phase 5 (UI) and Phase 6 (CI) do not revisit; 10 is blocked by two receiver-dependent `Block::info` impls (`wafer-run/src/wasm/wasmi_loader/mod.rs:1016-1024`, `wafer-core/src/service_blocks/auth.rs:22`) and would need a parallel opt-in static registry for a consumer benefit measured in one `NoopProviderAdmin` construction per `all_block_infos()` call; 13b (in-segment params, literal-beats-param precedence) would require relaxing `wafer-block/src/executor.rs:93-100` *and* `wafer-core/src/discovery.rs:1433-1442` together — the second exists precisely to stop the projection lying about the matcher — plus a specificity sort in `wafer-block-router/src/lib.rs:171`, for a consumer feature (`app-{hash}.css`) nobody has asked for. The honest counter-argument: a second pin bump is expensive, so anything we skip now is effectively skipped until another phase needs a bump. Items 2 and 3 are ~60 lines each and additive; if you want insurance, item 2 is the one to add to producer PR 2.

**5.4 Where the single OpenAI codec lives.** Recommend **`impresspress-core/src/blocks/llm/providers/openai.rs`, not `wafer-core::interfaces::llm`** — conditional on 5.1 ruling for the core dependency. Evidence: the producer contains **zero** OpenAI code today — six repo-wide hits, all prose or one test-fixture string (`wafer-block/src/wire/llm.rs:488`) — and no SSE framing anywhere; `interfaces/llm/service.rs:5-11` states the design position that its types are the canonical wire types with "no conversion layer". Putting the first vendor-protocol codec into wafer-core makes the framework own a third party's wire format it has deliberately avoided, and it puts a codec used by exactly one consumer behind a pin bump for every future fix to it. With the browser depending on `impresspress-core` (5.1), one codec in the consumer reaches both consumers with no pin involved. The review says upstream; this is the one place I would overrule it. If 5.1 rules against the core dependency, then upstream becomes the only shared home and item 12 must be added to producer PR 2 — which is why 5.1 must be ruled first.

**5.5 Does the Cloudflare request path run `seed_after_admin_init`?** *(The premise of this recommendation is false; see the amendment to ruling 5.5 at the top of this document, which replaces it.)* Recommend **yes, with `CfBootHooks` passed on all three paths.** Evidence: it is skipped today only because the request path never went through `boot` (`impresspress-cloudflare/src/lib.rs:1831-1833`), not because anyone decided it should be; `CfBootHooks::seed_after_admin_init` (`:1844-1861`) is a block-settings load-and-seed plus a snapshot republish, which the request path *already* performs inline in `build_runtime` (`:1138-1170`), so passing the hook removes a copy rather than adding work. The alternative — `hooks: None` on the request path — is defensible but must be a written decision at the call site, because the current state is an accident that the review found by reading three files. Whichever way it goes, the seed's cost on a cold isolate should be measured in PR 5 and stated.

**5.6 B9's fix shape, and whether Cloudflare gets `block-llm`/`block-vector`.** Recommend **keep the provider routes declared and answer 501 from a `Result`-returning `configure`; add the CF passthroughs but leave them out of `default` and `full`.** Evidence for the first half: `blocks/mod.rs:113-117` and `test_support::real_block_infos()` both build `LlmBlock::new(NoopProviderAdmin)`, so an endpoint set conditional on the handle would delete the provider rows from `llm.openapi.json` and `llm.endpoints.json` in every snapshot build — the published surface would then describe the *snapshot's* build rather than any real deployment, which is exactly the vacuous-gate failure `LEGITIMATELY_EMPTY = &[]` (`tests/openapi_snapshot.rs:63`) was added to prevent. Evidence for the second: the stale exclusion comment (`impresspress-cloudflare/Cargo.toml:86-88`) is wrong on all three of its claims and `impresspress-web` ships both features, so there is no technical reason to forbid them — but this repo targets Cloudflare Workers where wasm size is a measured constraint, `default = []` is a deliberate lean-by-default (`:16-27`), and turning them on by default would add block modules to every Worker bundle. Making them *available* costs nothing; making them *default* needs a size measurement, which PR 8 should report either way.

**5.7 `after_mutation` and the KV cache.** Recommend **no**, as in 5.3. Raised separately because the review names it as the structural closure of B6, and it is worth being explicit that B6 was closed differently (refuse, not invalidate) and that the forwarder macro is what makes the refusal *unforgettable*.

**5.8 The CLI's typestate deploy and `deploy.rs` split.** Recommend **deferred, and say so in the spec rather than leaving it implied.** Evidence: the review's two loudest CLI findings are already closed — there are zero `std::process::Command` sites left (every spawn is `tokio::process::Command`) and B7's raw-rusqlite loader is gone (`server_config.rs` is 28 lines) — and section 8 of the review itself refutes "giant functions in deploy.rs" (max 77 lines). What remains is size (`deploy.rs` 1,744 lines, `embed_cloudflare::deploy` 513, `wrangler::generate_named` 8 parameters at `wrangler.rs:185-194`) and a runtime-threaded gate for a statically fixed order. That is a pure structural refactor of the one code path with **no** CI coverage — `impresspress deploy` is invisible to the dry-run goldens and never runs in any workflow — so its risk-to-value ratio in an unattended run is the worst in the phase. PR 9 takes only the shared-contract half (release manifest, `RELEASES_ROOT`, the report twins, `schema_version`), which is where the actual runtime-breaking drift lives.
